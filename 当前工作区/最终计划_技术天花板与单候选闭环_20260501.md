# 最终计划：技术天花板判断、经验教训与单候选闭环

作者：**Manus AI**  
日期：2026-05-01  
适用仓库：`Yaahua/bisai`  
当前可信底座：`submit_v44_del_var_con_cross`，A 榜已知最高可信分数 **0.4514**

## 一、最终判断：不是绝对到底，但“直接改提交文件”的技术路线已经接近局部天花板

当前最重要的结论是：**0.4514 不是理论上不可突破的绝对上限，但以人工启发式、低频删除、方向删除、历史共识单条加法为核心的直接改 JSON 路线，已经进入极窄的局部天花板区间**。仓库 README 记录第一名为 **0.4560**，当前底座 **0.4514** 与第一名差距约 **0.0046**，这说明榜单上仍存在可压榨空间；但连续三个候选落到 **0.4167、0.4164、0.4162**，说明继续用同一套“看起来合理就改一点”的方式，风险远大于收益。

> **一句话结论**：还能压榨，但不能再靠批量候选、低频消融或大模型直接生成来压榨；剩余空间只适合通过“离线证据工厂 + 线上单候选提交”的方式一点点挤出。

本轮审计确认，`当前工作区/底座/submit_baseline_04514_v44_del_var_con_cross.json` 是一个 400 条样本、288 条含关系样本、1052 条关系的列表型提交文件；对应 zip 内部只有 `submit.json`，大小为 740,359 字节。这说明后续工作应以该底座为唯一派生源，而不是回到旧目录或继续使用 v46/v46b 体系。此前广域学术检索也不支持“直接用 LLM 或外部工具生成最终提交”，更支持 data-centric 处理、方向角色、关系特定 QA、候选证据表和保守后处理的组合路线。[1] [2] [3] [4]

| 判断对象 | 当前结论 | 理由 | 操作含义 |
|---|---|---|---|
| 0.4514 底座本身 | 未必是绝对极限 | 与第一名仍有约 0.0046 差距，历史 v41 到 v44 仍能小涨 | 可以继续做极小步冲分 |
| 直接启发式删关系 | 基本证伪 | `GENE-LOI-MRK` 删除和 `GENE-CON-TRT` 单条删除均跌至 0.416x | 冻结删除、消融、低频判噪声 |
| v46/v46b 候选体系 | 整体冻结 | 删除失败后，单条加法也跌至 0.4162，说明不只是“删除方向错” | 不再提交任何已生成 v46/v46b 包 |
| 大模型直接生成 | 不可作为提交主线 | 生成式 RE 往往高召回低精度；论文和仓库历史都提示容易引入噪声 | 只作为离线判别器和证据解释器 |
| 剩余可压榨空间 | 存在但很窄 | 榜首差距小，公开榜反馈对单条变化异常敏感 | 每次最多 1 个候选，且必须能解释 |

## 二、经验教训统一记录

第一条经验是，**低频不等于假阳性**。此前的 v46/v46b 路线把训练频次低、方向异常、样本簇可疑作为主要删除依据，但实际榜单反馈显示，删除 5 条 `GENE-LOI-MRK` 后从 0.4514 降到 0.4167，删除 1 条 `GENE-CON-TRT` 后降到 0.4164。这种幅度不是普通抖动，而是说明被删关系中很可能含有公开榜关键真阳性，或者候选文件体系与真实底座存在偏差。

第二条经验是，**单条加法也不能脱离文件体系审计**。`submit_v46b_micro_add_consensus_01_49_var_con_cross.zip` 原本看起来是高语义、历史共识、只补不删的加法，但结果仍然是 0.4162。这个结果迫使我们把问题从“某个关系判断错了”上升到“候选体系、底座身份、打包版本、历史文件来源可能有根本异常”。因此，只要某个候选来源于 v46/v46b 旧体系，即使它是单条加法，也不能再直接上传。

第三条经验是，**学术方法只能改变离线搜索能力，不能替代线上提交纪律**。BioRED、BioREx、关系特定 QA、LLM-IE 和 data-centric ensemble 等方向证明，高分系统通常来自数据清洗、schema 对齐、候选生成、判别式 QA、预处理鲁棒性和集成，而不是把论文方法直接搬成一个提交文件。[1] [2] [3] [4] 对当前仓库而言，学术路线的正确用法是扩大离线候选发现，再用极严格的证据闸门筛出一个候选。

| 失败或观察 | 原先误判 | 新经验 | 以后规则 |
|---|---|---|---|
| 0.4167 | 方向异常关系可以整族删除 | 公开榜可能保留这些关系，方向统计不能直接等于真值 | 禁止整族删除 |
| 0.4164 | 单条低频删除风险可控 | 单条删除也可能击中关键真阳性 | 禁止低频微消融 |
| 0.4162 | 历史共识单条加法较安全 | 候选文件体系异常时，加法也会失败 | 禁止继续上传 v46/v46b 旧包 |
| 0.4514 | 还有很多启发式空间 | 空间存在但极窄，任何错误都可能大回撤 | 一次只做一个强证据候选 |
| 学术检索 | 找到新方法即可冲分 | 新方法只适合做离线证据层 | 大模型、外部工具不得直接生成提交 |

## 三、大模型方案的取舍：排除“直接生成”，保留“离线裁判”

大模型方案不是完全没用，但必须重新定义边界。当前明确排除三类方案：第一，排除让大模型直接读测试文本并自由生成关系；第二，排除让大模型批量修正 JSON 后直接打包；第三，排除把外部 BioRED、PubTator、STRING 或 BioREx schema 直接映射为天池提交。相关工具和论文都提示，生成式信息抽取系统可扩大召回，但在多关系、多实体、schema 不完全一致时很容易牺牲精度。[3] [4]

保留的大模型用法只有一种：**判别式离线裁判**。也就是说，大模型只能在已经固定的候选三元组上回答结构化问题，例如 `supported / reversed / unsupported / ambiguous`，并给出文本证据位置、实体类型是否匹配、方向是否符合训练语义。它不能决定最终提交，最终提交仍必须通过候选证据表、人工复核、脚本 diff 和单候选账本。

| 大模型/外部方案 | 是否保留 | 原因 | 允许形式 |
|---|---|---|---|
| LLM 直接生成全部关系 | 排除 | 高召回低精度，极易引入假阳性 | 不允许 |
| LLM 批量改 JSON | 排除 | 不可归因，失败后无法定位 | 不允许 |
| LLM 判别固定候选 | 保留 | 可给出证据标签和解释，辅助人工筛选 | 只输出 `supported/reversed/unsupported/ambiguous` |
| BioREx/PubTator/STRING 直接映射 | 排除 | 天池作物育种 schema 与通用 biomedical schema 不一致 | 不允许直接入提交 |
| 外部证据作排序特征 | 保留 | 可辅助发现漏项或反证弱候选 | 只能进入证据表低权重字段 |
| 多模型投票直接提交 | 排除 | 历史已有投票加法掉分风险，一致性不是充分条件 | 只能作为历史稳定性特征 |

## 四、剩余可压榨空间在哪里

剩余空间不在“再删一些看着可疑的关系”，也不在“让大模型再补一批关系”。更现实的空间有三类：第一，**底座身份和历史涨分最小差异复核**，即确认 0.4514 的真实来源和 v41→v44 的有效涨分机制；第二，**人工证据表驱动的单条补召回**，即只在文本证据、训练类型、历史版本、方向语义全部支持时补一条关系；第三，**方向边界的非提交式审计**，即继续建立方向混淆矩阵，但在没有新增强证据前不再做删除或换向提交。

从收益预期看，当前不应追求一次性大涨。更合理的目标是先保护 0.4514，尝试挤出 **+0.0002 到 +0.0010** 的小幅收益；如果有连续两个可解释单候选涨分，再考虑组合已验证原子操作。若一个候选失败，立即回滚并修订证据闸门，而不是继续提交同源候选。

| 可压榨方向 | 预期收益 | 当前优先级 | 前置条件 | 风险 |
|---|---:|---:|---|---|
| 底座身份复核与历史差异还原 | 间接收益 | 最高 | 确认 zip、JSON、样本数、关系数、历史分数一一对应 | 无直接上榜风险 |
| 高证据单条补召回 | +0.0002 至 +0.0010 | 高 | 证据表中全部闸门通过 | 错加可能回撤 |
| 已涨分原子操作组合 | +0.0002 至 +0.0010 | 中 | 至少两个原子操作分别涨分 | 未验证组合仍可能互相抵消 |
| 方向矩阵审计 | 间接收益 | 中 | 只审计不提交 | 若过早换向会重复失败 |
| 外部弱监督候选发现 | 长期收益 | 低到中 | schema 对齐、人工复核 | 噪声大、迁移偏差高 |

## 五、最终执行闭环：反复试错、反复记录、反复调整，但每轮只有一个候选

后续流程固定为 **六步闭环**：复核底座、提出一个假设、建立证据表、生成一个候选、提交后记录、根据分数调整计划。这个闭环的重点不是“少做事”，而是让每一次试错都能产生确定知识。无论涨分还是跌分，都必须更新经验教训和禁忌清单，然后才允许进入下一轮。

> **硬纪律**：没有证据表，不生成候选；没有 diff，不打包；没有提交账本，不上传；没有分数反馈，不做下一候选。

| 步骤 | 动作 | 产物 | 通过标准 | 不通过处理 |
|---:|---|---|---|---|
| 1 | 复核底座身份 | `底座身份审计.md` | 样本数 400、关系数 1052、zip 内 `submit.json` 一致 | 停止冲分，先修复底座 |
| 2 | 提出一个假设 | `候选假设卡.md` | 假设只涉及一条关系或一个最小可归因操作 | 拆小或放弃 |
| 3 | 建立证据表 | `candidate_evidence_table.csv` 的一行 | 文本证据、实体类型、方向、历史稳定性均明确 | 标记 review，不提交 |
| 4 | 生成一个候选 | 一个 JSON + 一个 ZIP | `validate_submission.py` 通过，diff 只含预期变化 | 删除候选文件 |
| 5 | 上传并记录 | `提交账本.md` | 记录文件名、假设、diff、平台分数 | 未记录不得继续 |
| 6 | 调整计划 | 更新最终计划或禁忌记录 | 涨分则允许下一同源候选；跌分则冻结同源路线 | 回到底座重审 |

## 六、下一轮具体计划

下一轮不直接从 v46/v46b 旧候选中挑文件上传。第一步只做底座身份复核和历史涨分链复核，确认 `submit_v44_del_var_con_cross` 的 JSON 与 zip 在当前工作区中完全可复现。第二步建立一张极小的候选证据表，优先从历史真正涨分的 v36、v41、v44 差异中寻找“曾经带来收益但未完全利用”的模式，而不是从失败候选中继续挖。第三步只选择一条最强候选，生成全新命名的 `v47_single_*` 文件，且文件必须从当前工作区底座复制派生。

如果下一条候选高于 0.4514，则只允许沿同一证据类型再做一条；如果等于或接近 0.4514，则暂停提交，继续增强证据表；如果低于 0.4514，则冻结该候选类型，写入禁忌记录，并回到底座。

| 阶段 | 目标 | 允许做什么 | 禁止做什么 |
|---|---|---|---|
| A | 保护底座 | 审计当前工作区底座、历史分数链、zip 结构 | 修改 JSON 内容 |
| B | 找候选 | 从真实涨分历史和文本证据中找 1 条候选 | 批量生成、从 v46/v46b 归档恢复提交 |
| C | 生成提交 | 新建 `v47_single_*` 一个文件 | 使用 `v46`、`v46b`、`micro_del`、`micro_add_consensus` 命名 |
| D | 提交后记录 | 写入提交账本和经验教训 | 未记录分数就继续下一轮 |
| E | 调整计划 | 涨分扩展、持平暂停、跌分冻结 | 用榜单继续蒙方向 |

## 八、最终红线

最终红线可以概括为五条。第一，**不再提交任何 v46/v46b 旧候选**。第二，**不再删除或低频消融 v44 中的关系**，除非先有新的、独立的、强人工证据，并且仍需单条提交。第三，**不让大模型直接生成最终答案**，它只能做离线判别和解释。第四，**每次最多一个候选**，不能为了节省时间批量生成。第五，**每次试错都必须沉淀为记录**，否则同一错误会在不同文件名下反复发生。

> **最终执行口径**：当前技术没有绝对到底，但已经不适合靠“再试几个文件”压榨。剩余收益只能来自证据质量，而不是候选数量。
